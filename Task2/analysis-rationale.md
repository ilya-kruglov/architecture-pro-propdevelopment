**Дата:** 2026-04-06  
**Автор:** Студент Яндекс Практикум, курс "Архитектура ПО: продвинутый уровень (System Design)"

## Контекст проблем компании

На основе описания системы PropDevelopment были выявлены следующие ключевые проблемы безопасности:

1. **Нарушен контроль данных** — множественные точки регистрации нового клиента, отсутствие координации между ними
2. **Проблемы с API партнёров** — контракты API содержат категории данных, которые явно предоставляют персональные данные; некоторые контракты позволяют внешним пользователям выполнять действия и получать данные, к которым у них не должно быть доступа
3. **Отсутствие ограничений доступа в DWH** — со стороны систем обработки данных нет ограничений на доступ к данным
4. **Утечки данных в ЛК клиентов** — клиенты видят в приложении ошибки, там иногда отображаются данные другого клиента (чужое ФИО)
5. **Нарушен процесс передачи информации** — из-за изменений в составе руководителей IT-команд специалисту по ИБ передают не все решения и изменения

## Обоснование выбора разделов

| Раздел | Приоритет | Обоснование |
|--------|-----------|-------------|
| **I. Управление доступом** | Критический | Компания имеет множественные точки регистрации клиентов, отсутствует координация. Клиенты видят чужие данные в ЛК — явный признак проблем с RBAC (Role-Based Access Control) и изоляцией данных на уровне приложений и БД. Отсутствие единого реестра учётных записей и централизованного контроля доступа усугубляет ситуацию. |
| **II. Безопасность данных** | Критический | API партнёров передают избыточные ПДн, нет ограничений доступа в DWH, нет единых политик безопасности для API. Это прямой путь к утечке. Также отсутствует классификация данных и контроль целостности (клиенты видят чужие данные). |
| **III. Защита инфраструктуры** | Высокий | Есть firewall на периметре, но неизвестно о сегментации сети, IDS/IPS, контроле трафика между внутренними сегментами. Существует риск lateral movement (горизонтального перемещения) после взлома одного сервиса. Использование гибридной облачной инфраструктуры добавляет риски. |
| **IV. Управление инцидентами** | Высокий | Недавно у конкурента произошла утечка данных, которая активно обсуждалась в СМИ. Руководство PropDevelopment обеспокоено. Компания не может эффективно реагировать на инциденты без плана реагирования, SIEM-системы и регулярных учений. |
| **V.1. Общие вопросы (MDM, VPN, облачные бэкапы)** | Средний | У компании есть мобильное приложение для собственников. Необходимо понимать, используются ли MDM для корпоративных устройств, VPN для удалённого доступа сотрудников, а также как контролируются бэкапы в облачной среде. Эти вопросы не являются первоочередными, но важны для комплексной безопасности. |
| **V.2. Управление оборудованием и физической безопасностью** | Низкий | В описании системы нет упоминаний проблем с физической безопасностью, серверными помещениями или утилизацией оборудования. Базовые вопросы включены для полноты проверочного листа, но приоритет этого раздела — самый низкий в контексте текущих проблем компании. |

---

## Разделы, исключённые из шаблона

**Нет — все разделы релевантны.** Шаблон, предоставленный в уроке, полностью покрывает необходимые области проверки. Раздел V.2 (физическая безопасность) имеет наименьший вес, но исключать его нецелесообразно, так как базовые меры физической безопасности всегда должны быть задокументированы.

## Связь с проблемами бизнеса

| Проблема бизнеса | Соответствующие разделы проверочного листа |
|------------------|-------------------------------------------|
| Повысить удовлетворённость клиентов (ошибки с чужими данными) | I. Управление доступом, II. Безопасность данных |
| Расширять направление обработки данных (BI/ML/AI) | II. Безопасность данных (классификация, контроль доступа в DWH) |
| Отреагировать на инциденты и рыночные изменения (утечка у конкурента) | IV. Управление инцидентами |
| Соответствие требованиям законодательства РФ | II. Безопасность данных (ПДн, классификация), I. Управление доступом |

## Заключение

Проверочный лист сфокусирован на **критических** и **высокоприоритетных** разделах, которые напрямую связаны с выявленными проблемами компании. Разделы со средним и низким приоритетом включены для полноты картины, но не являются блокерами для немедленных действий по улучшению безопасности.
