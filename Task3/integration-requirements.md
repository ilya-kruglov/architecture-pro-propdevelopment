# Требования к внешним интеграциям: Умный дом

**Компания:** PropDevelopment  
**Партнёр:** Smart Home Provider  
**Сервисы:** Интеллектуальный домофон, Интеллектуальный шлагбаум  
**Дата:** 2026-04-06

---

## 1. Требования к безопасности

### 1.1. Защита данных при передаче

| № | Требование | Обоснование |
|---|------------|-------------|
| R1.1.1 | Все взаимодействия между PropDevelopment и Smart Home Provider должны осуществляться исключительно по протоколу **HTTPS (TLS 1.3)** | Предотвращение перехвата и модификации трафика (Man-in-the-Middle) |
| R1.1.2 | Должен использоваться **mTLS (Mutual TLS)** для двусторонней аутентификации серверов | Обеспечение доверия между системами, предотвращение подделки запросов |
| R1.1.3 | Сертификаты должны выпускаться доверенным удостоверяющим центром (или внутренним PKI с согласованной цепочкой доверия) | Гарантия подлинности сторон |
| R1.1.4 | Срок действия сертификатов не должен превышать 1 года, автоматическое обновление (auto-renewal) обязательно | Снижение риска компрометации долгоживущих сертификатов |

### 1.2. Аутентификация и авторизация

| № | Требование | Обоснование |
|---|------------|-------------|
| R1.2.1 | PropDevelopment должен предоставлять **JWT (JSON Web Token)** для каждого запроса к API партнёра | Децентрализованная проверка прав, отсутствие необходимости в session state |
| R1.2.2 | JWT должен содержать следующие claims: `sub` (идентификатор собственника), `tenant_id` (идентификатор ЖК), `device_id` (опционально), `exp` (время истечения) | Контекстная авторизация на стороне партнёра |
| R1.2.3 | Время жизни JWT не должно превышать **15 минут** для операций управления и **1 час** для read-операций | Ограничение окна атаки при компрометации токена |
| R1.2.4 | Smart Home Provider должен поддерживать **refresh token** механизм (без хранения состояния на стороне PropDevelopment) | Удобство пользователя без снижения безопасности |
| R1.2.5 | Для сервис-ту-сервис вызовов (например, синхронизация состояния устройств) должен использоваться **API Key** + **mTLS** | Дополнительный слой защиты для бэкенд-коммуникаций |
| R1.2.6 | API Key должен храниться в **secrets manager** (HashiCorp Vault / AWS Secrets Manager), не в коде и не в конфигурационных файлах | Предотвращение утечки секретов в репозиториях |

### 1.3. Обработка персональных данных (ПДн)

| № | Требование | Обоснование |
|---|------------|-------------|
| R1.3.1 | Партнёр НЕ должен хранить биометрические данные (слепки лиц). Биометрическая верификация должна выполняться на устройстве (домофон) или в изолированном модуле провайдера без передачи сырых биометрических данных в PropDevelopment | Соответствие законодательству РФ о биометрических ПДн (152-ФЗ) |
| R1.3.2 | При передаче номеров автомобилей в запросах на открытие шлагбаума должен использоваться **хеш** (SHA-256 с солью) вместо plaintext | Минимизация объёма передаваемых ПДн |
| R1.3.3 | Партнёр должен предоставить документы, подтверждающие соответствие требованиям **152-ФЗ «О персональных данных»** | Юридическая ответственность за обработку ПДн |
| R1.3.4 | В договоре с партнёром должен быть прописан пункт о запрете передачи ПДн третьим лицам и обязанности уведомлять об инцидентах в течение 24 часов | Снижение рисков утечки через партнёра |

### 1.4. Журналирование и аудит

| № | Требование | Обоснование |
|---|------------|-------------|
| R1.4.1 | Smart Home Provider должен предоставлять **логи доступа** (кто, когда, какое действие, с каким устройством) в машиночитаемом формате (JSON) | Аудит инцидентов, расследование утечек |
| R1.4.2 | Логи должны храниться не менее **90 дней** | Соответствие требованиям аудита |
| R1.4.3 | PropDevelopment должен логировать все запросы к адаптеру `smart-home-integration` с уровнем детализации INFO (включая user_id, device_id, action, status) | Восстановление цепочки действий при инцидентах |

### 1.5. Управление инцидентами

| № | Требование | Обоснование |
|---|------------|-------------|
| R1.5.1 | Партнёр обязан уведомлять PropDevelopment о любых инцидентах безопасности в течение **24 часов** с момента обнаружения | Быстрое реагирование, снижение последствий |
| R1.5.2 | У партнёра должен быть задокументированный план реагирования на инциденты (IRP) | Гарантия наличия процессов |
| R1.5.3 | В SLA должна быть включена метрика **MTTR (Mean Time To Respond)** для критических уязвимостей — не более 48 часов | Ожидаемый уровень сервиса |

## 2. Протоколы аутентификации и авторизации

### 2.1. Схема аутентификации
| Шаг | Компонент | Направление | Компонент | Протокол |
|:----:|-----------|:-----------:|-----------|----------|
| 1 | Mobile App (собственник) | ─────▶ | tenant-core-app | HTTPS / REST |
| 2 | tenant-core-app | ─────▶ | smart-home-integration | gRPC / REST + JWT |
| 3 | smart-home-integration | ─────▶ | Smart Home Provider API | HTTPS / mTLS + JWT |
| 4 | Smart Home Provider API | ─────▶ | Устройства (домофон, шлагбаум) | MQTT over TLS |


### 2.2. Последовательность аутентификации

| Шаг | Отправитель | Получатель | Действие | Протокол |
|-----|-------------|------------|----------|----------|
| 1 | Mobile App | tenant-core-app | Передача JWT пользователя (полученный от Keycloak) | HTTPS / REST |
| 2 | tenant-core-app | smart-home-integration | Валидация JWT, извлечение user_id и tenant_id. Генерация нового service JWT для внешнего API | gRPC / REST |
| 3 | smart-home-integration | Smart Home Provider API | mTLS handshake + передача JWT в заголовке `Authorization: Bearer <jwt>` | HTTPS / mTLS |
| 4 | Smart Home Provider | Устройство | Внутренняя аутентификация провайдера (out of scope для PropDevelopment) | Внутренний протокол |

### 2.3. Формат JWT (пример)

```json
{
  "header": {
    "alg": "RS256",
    "typ": "JWT"
  },
  "payload": {
    "sub": "user-12345",
    "tenant_id": "housing-complex-789",
    "device_id": "intercom-main-door",
    "role": "owner",
    "permissions": ["door.open", "barrier.open", "camera.view"],
    "iat": 1744012800,
    "exp": 1744013700,
    "jti": "unique-token-id-98765"
  }
}
```

### 2.4. Методы авторизации на стороне партнёра

| Метод | Использование |
|-------|---------------|
| **RBAC** (Role-Based Access Control) | Проверка роли `owner` для доступа к управлению устройствами |
| **ABAC** (Attribute-Based Access Control) | Проверка `tenant_id` — собственник может управлять только устройствами в своём ЖК |
| **Time-based** | Запрет открытия шлагбаума в ночное время (00:00-06:00) для неавторизованных автомобилей |

## 3. Организация взаимодействия между системами

### 3.1. Архитектурная схема взаимодействия

#### Уровень 1: PropDevelopment (внутренний периметр)

| Компонент | Роль | Взаимодействие |
|-----------|------|----------------|
| **Keycloak** | Сервис аутентификации | Взаимодействует с tenant-core-app (аутентификация пользователей) |
| **tenant-core-app** | Бэкенд для собственников | Получает JWT от Keycloak, вызывает smart-home-integration |
| **smart-home-integration** | API Gateway / Адаптер | Единственный компонент с доступом к внешнему API партнёра |
| **Redis** | Кэш токенов | Хранит JWT для снижения нагрузки на аутентификацию |
| **PostgreSQL** | База данных арендаторов | Хранит tenant_id, настройки устройств, права доступа |

**Связи внутри периметра:**
- Keycloak ◀──▶ tenant-core-app (аутентификация, выдача JWT)
- tenant-core-app ──▶ smart-home-integration (вызов управления устройствами)
- smart-home-integration ──▶ Redis (кэширование токенов)
- tenant-core-app ──▶ PostgreSQL (чтение/запись данных пользователей)

#### Уровень 2: Smart Home Provider (DMZ / внешний периметр)

| Компонент | Функции | Технологии |
|-----------|---------|------------|
| **API Gateway (партнёра)** | Проверка mTLS, валидация JWT, Rate limiting (100 req/min/user) | HTTPS / mTLS |
| **Device Management Service** | Маршрутизация к устройствам, логирование действий | gRPC / REST |
| **IoT Hub** | Управление IoT-устройствами | MQTT / WebSocket |

**Связь между уровнями:**
PropDevelopment (smart-home-integration)
│
│ (mTLS + JWT)
▼
Smart Home Provider (API Gateway)
│
│ (внутренний API)
▼
Device Management Service
│
│ (MQTT over TLS)
▼
IoT Hub

#### Уровень 3: Устройства (физические)

| Устройство | Функции | Протокол связи |
|------------|---------|----------------|
| **Smart Intercom** (интеллектуальный домофон) | Открытие по звонку, распознавание по лицу, автоматическое открытие | MQTT over TLS |
| **Smart Barrier** (интеллектуальный шлагбаум) | Управление шлагбаумом, распознавание номеров автомобилей | MQTT over TLS |

### 3.1.1. Сводная таблица потоков данных

| Отправитель | Получатель | Протокол | Данные | Защита |
|-------------|------------|----------|--------|--------|
| Mobile App | tenant-core-app | HTTPS / REST | Запрос на открытие + JWT пользователя | TLS 1.3 |
| tenant-core-app | smart-home-integration | gRPC / REST | user_id, tenant_id, device_id, action | JWT + TLS |
| smart-home-integration | API Gateway (партнёр) | HTTPS / mTLS | JWT (service), device_id, action | mTLS + JWT |
| API Gateway | Device Management Service | gRPC | Внутренние вызовы | Внутренняя сеть |
| Device Management Service | IoT Hub | MQTT over TLS | Команды управления | TLS 1.3 |
| IoT Hub | Smart Intercom / Barrier | MQTT over TLS | Сигнал открытия | TLS 1.3 + Device cert |

### 3.1.2. Сквозной сценарий: открытие домофона

| Шаг | Компонент | Действие | Протокол |
|:----:|-----------|----------|----------|
| 1 | Mobile App | Пользователь нажимает "Открыть дверь" | — |
| 2 | tenant-core-app | Валидирует JWT пользователя, проверяет права (tenant_id, role) | HTTPS |
| 3 | smart-home-integration | Генерирует service JWT, вызывает API партнёра | mTLS + JWT |
| 4 | API Gateway (партнёр) | Проверяет mTLS, валидирует JWT, применяет rate limiting | — |
| 5 | Device Management Service | Определяет IP адрес устройства, отправляет команду | gRPC |
| 6 | IoT Hub | Публикует команду в MQTT topic `/devices/{id}/open` | MQTT over TLS |
| 7 | Smart Intercom | Получает команду, открывает дверь | — |
| 8 | IoT Hub | Публикует подтверждение в topic `/devices/{id}/status` | MQTT over TLS |
| 9 | Device Management Service | Логирует действие (user_id, device_id, timestamp, result) | — |
| 10 | API Gateway | Возвращает HTTP 200 OK с confirmation_id | HTTPS |
| 11 | smart-home-integration | Кэширует ответ, возвращает статус в tenant-core-app | — |
| 12 | Mobile App | Отображает "Дверь открыта" | — |

### 3.2. Требования к API партнёра

| № | Требование | Описание |
|---|------------|----------|
| R3.2.1 | REST API с OpenAPI 3.0 спецификацией | Документированные контракты |
| R3.2.2 | Эндпоинты управления домофоном | `POST /api/v1/intercom/{device_id}/open`, `GET /api/v1/intercom/{device_id}/status` |
| R3.2.3 | Эндпоинты управления шлагбаумом | `POST /api/v1/barrier/{device_id}/open`, `GET /api/v1/barrier/{device_id}/status` |
| R3.2.4 | Эндпоинт для верификации | `POST /api/v1/verify` (проверка токена без выполнения действия) |
| R3.2.5 | Rate limiting | Не более 100 запросов в минуту на одного пользователя |
| R3.2.6 | Retry policy | При ошибках 5xx — повтор через 1, 2, 4 секунды (максимум 3 попытки) |

### 3.3. Требования к адаптеру `smart-home-integration` (PropDevelopment)

| № | Требование | Описание |
|---|------------|----------|
| R3.3.1 | Изоляция внешнего API | Адаптер — единственный компонент, имеющий сетевой доступ к внешнему API партнёра |
| R3.3.2 | Трансформация данных | Преобразование внутренних форматов данных в формат партнёра и обратно |
| R3.3.3 | Кэширование | Кэширование JWT (с учётом времени жизни) для снижения нагрузки на аутентификацию |
| R3.3.4 | Circuit Breaker | Реализация паттерна Circuit Breaker для защиты от отказа внешнего API |
| R3.3.5 | Health checks | Эндпоинт `/health` и `/ready` для Kubernetes |
| R3.3.6 | Метрики | Prometheus-метрики: количество запросов, ошибки, latency |

### 3.4. Сетевые требования

| № | Требование | Значение |
|---|------------|----------|
| R3.4.1 | Протокол | HTTPS (TLS 1.3) |
| R3.4.2 | Порты | 443 (основной), 8443 (резервный) |
| R3.4.3 | IP-адреса партнёра | Должны быть предоставлены и зафиксированы в Firewall rules (allowlist) |

| R3.4.5 | Timeout | Connection timeout: 5 сек, Request timeout: 30 сек |

## 4. Матрица ответственности (RACI)

*R — Responsible, A — Accountable, C — Consulted, I — Informed*

| Деятельность | PropDevelopment | Smart Home Provider |
|--------------|:---------------:|:-------------------:|
| Аутентификация пользователей | R (Keycloak) | A |
| Генерация и подписание JWT | R | I |
| Валидация JWT на стороне партнёра | I | R |
| Хранение биометрических данных | A (не хранить) | R (только на устройстве) |
| Логирование действий пользователей | R (свои логи) | R (логи доступа к устройствам) |
| Реагирование на инциденты безопасности | A | R |
| Резервное копирование конфигураций устройств | I | R |
| Обеспечение uptime API (99.9%) | I | R |

## 5. Чек-лист для приёмки интеграции

- [ ] mTLS настроен и работает (проверка с использованием тестовых сертификатов)
- [ ] JWT валидируется с правильной подписью (RS256)
- [ ] Rate limiting работает (100 req/min/user)
- [ ] Логи аудита передаются в PropDevelopment в формате JSON
- [ ] Подписан договор о обработке ПДн (включая запрет передачи биометрии)
- [ ] Проведено пентест-тестирование API партнёра (результаты предоставлены)
- [ ] SLA подписано (uptime 99.9%, MTTR < 4 часа для критических инцидентов)
- [ ] Разработана документация API (OpenAPI 3.0)
- [ ] Настроен мониторинг доступности API партнёра из сети PropDevelopment
- [ ] Проведено нагрузочное тестирование (1000 RPS, проверка timeout и retry policy)
